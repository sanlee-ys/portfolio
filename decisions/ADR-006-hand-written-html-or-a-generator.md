# ADR-006: Hand-written HTML, or a static site generator?

**Status:** **Proposed — no decision made.** This is a stub, written to hold the
evidence and the question so the next session does not re-derive either. Nothing
here commits the site to anything. The deciding session must fill in *Decision*
and *Consequences* and move the status to Accepted or Rejected.
**Date:** 2026-07-26 (question opened)
**Deciders:** San Lee

---

## Context

The site is 13 hand-written HTML pages plus one 1,296-line stylesheet, with no
build step. `CLAUDE.md` states that property in its opening line, and it has been
a deliberate one: no toolchain, no `node_modules` in the serving path, nothing
between a file and what GitHub Pages ships.

The question was opened on 2026-07-26 by an adversarial review of the front-end,
prompted by a plain complaint: *the site is too much information density — a whole
lot of scrolling and reading.*

### What the complaint measures out to

Measured with Playwright at a 900px-tall viewport, not estimated:

| Page | Words | Read time | Screens |
|---|---|---|---|
| Classifier | 3,194 | 14.5 min | 10.1 |
| The System | 1,959 | 8.9 min | 7.6 |
| netops-lab | 1,760 | 8.0 min | 4.8 |
| Homepage | 1,405 | 6.4 min | 7.4 |
| Judge | 1,320 | 6.0 min | 4.0 |
| Glossary | 929 | 4.2 min | 4.3 |
| Product & Program | 843 | 3.8 min | 3.7 |
| Colophon | 740 | 3.4 min | 2.7 |
| **Total (8 of 13 pages)** | **12,150** | **~55 min** | |

A recruiter gives a portfolio 30–90 seconds. A skeptical senior engineer who is
genuinely interested gives it perhaps five minutes. The site asks for 55.

### The finding that matters for this decision

**No front-end change fixes that.** Not one candidate below removes a single word,
and a migration undertaken to fix reading burden would be a category error — two
weeks of feeling productive while 12,150 words sit exactly where they were.

The honest case for a generator is narrower and different: **the substrate does
not cause the density, but it shapes it.** Adding a page means copying ~40 lines
of head, theme script, analytics and footer boilerplate by hand, so content
accretes into 3,000-word monoliths rather than splitting into pages. Until
2026-07-26, **1 of 13 pages carried site navigation** — from the classifier you
could not reach the judge without going home first — because duplicating a nav
across 12 files by hand was not worth it to anyone. That is a real UX defect
that the substrate produced.

### The trigger condition, and its correction

The review's first draft deferred this: *revisit when you next want to add three
or more pages.* San corrected it — the condition had already fired. Verified in
git rather than recalled:

- `projects/loop-replay.html` — added **2026-07-23** (PR #101)
- `projects/netops-lab.html` — added **2026-07-26** (PR #136)

Both landed **after** the 2026-07-19 direction to finish the autonomy-ladder spine
and open no fourth front. The "three or more" number was arbitrary and is not
worth defending; the substantive point is that page-adding is **ongoing**, so
"the site is basically static in size" was a false premise.

Treat the trigger as **met**. The open question is cost, benefit and timing — not
whether the condition fired.

### Work already done that bears on this

Six PRs merged 2026-07-26 in the session that opened this question. Two are
directly relevant:

- **#141** put the site nav on all 11 interior pages. It was generated by script
  rather than 11 hand edits, and its own commit message calls it *"deliberately
  throwaway plumbing if that migration happens"* — a layout component does this
  once.
- **#142** added an "On this page" ToC to the three pages over ~1,500 words, with
  a stable id written into every `<h2>`.

Both are exactly the work a layout system makes cheap, and both are the first
things that would collapse into components under a generator.

## Decision

**Not yet made.** See *Status*.

The deciding session should treat these as the two live options, and should reach
a verdict rather than deferring again:

1. **Stay hand-written static.** Free. Keeps the no-build property. Accepts N-file
   edits for any shared-chrome change and no search across 12k words.
2. **Migrate to Astro (or Eleventy).** Still ships static HTML with zero JS by
   default. Buys layouts/components, Markdown content, and a drop-in static search
   (Pagefind). Costs a build step, a toolchain, and a migration of 13 pages plus a
   1,296-line stylesheet.

The genuine crux — and the reason this is an ADR rather than a ticket — is
[`ADR-004`](ADR-004-retire-the-lab-as-the-vehicle.md), which establishes the
portfolio as a **front-end learning vehicle**. Hand-writing the HTML and CSS is
partly the point. Whether a generator undercuts that, or simply moves the learning
up a layer to components and content modelling, is a real question and not a
rhetorical one. **Answer it explicitly before weighing anything else**; every other
argument here is downstream of it.

## Downstream surfaces

*What a migration would have to touch. This list is the migration checklist if
option 2 is chosen, and it is why the decision is worth recording either way — the
constraints below are load-bearing and easy to discover too late.*

- **Seven CI gates in `.github/workflows/qa.yml`**, all of which read the built
  HTML and must keep passing:
  `scripts/link-check.cjs`, `scripts/check-published-metrics.cjs`,
  `scripts/private-repo-check.cjs`, `scripts/lint_decisions.py`,
  `scripts/mobile-qa.cjs`, `scripts/classify-review-outcome.test.cjs`, and the
  private-name pre-commit tests. Several walk `*.html` from the repo root; under a
  generator they must walk the **build output** instead, and that redirection is a
  silent-failure risk — a gate pointed at a directory with no HTML in it passes.
- **`scripts/check-published-metrics.cjs`** asserts published eval numbers against
  the classifier artifact (currently **25 metrics, v3.1.0**) by reading
  `data-metric` spans out of the markup. Any templating must preserve those spans
  verbatim. This is the highest-risk single item on the list.
- **`resume.html` must stay standalone.** It deliberately does not link
  `assets/style.css` — it carries its own inline `<style>` and, since #138, its own
  `@font-face` rules — because `scripts/resume-pdf.cjs` renders it offline and
  aborts every non-`file:` request. A generator that hoists shared CSS into a
  layout breaks `resume.pdf`.
- **`scripts/mobile-qa.cjs`** loads pages over `file://`. Generator output with
  absolute (`/assets/...`) URLs will not resolve that way; either the gate learns
  to serve the build, or the output keeps relative paths.
- **`assets/style.css` (1,296 lines)** is one hand-maintained file with substantial
  explanatory comments. Splitting it per-component is the tempting move and would
  scatter that reasoning; decide deliberately rather than by tooling default.
- **`ADR-004`** — the learning-vehicle premise, as above. If migration is chosen,
  ADR-004 needs an amendment saying what the learning vehicle now *is*, or it
  quietly becomes untrue.
- **`CLAUDE.md`** — its opening line states "static HTML/CSS, no build step; every
  page links `assets/style.css`", and its mobile-QA instructions assume the repo
  layout. Per this tier's *ADR records the why, `CLAUDE.md` keeps the rule* split,
  the operative instructions move there, not here.
- **`decisions/README.md`** — index row (added by this stub) and the narrative note
  when the question closes.
- **`.github/workflows/deploy-pages.yml`** — currently deploys the repo root. A
  build step changes what is uploaded.
- **`sitemap.xml`, `robots.txt`, `CNAME`, `404.html`** — hand-maintained today;
  a generator either owns them or must be told not to.
- **The 2026-07-19 direction ("finish the spine, no fourth front")** — a migration
  is a fourth front. If chosen, say so explicitly and re-sequence, rather than
  letting it happen alongside.
- **Not touched either way:** the content itself. Restating the finding above,
  because it is the thing most likely to be forgotten: no option here removes a
  word, and the density complaint is answered by information architecture, not by
  tooling.

## Alternatives Considered

*Already weighed and rejected in the 2026-07-26 review. Recorded so the deciding
session does not re-litigate them from scratch; reopen any of them with new
evidence, not with fresh enthusiasm.*

| Option | Reason Not Chosen |
|--------|-------------------|
| **Docs framework** (Starlight, Docusaurus, MkDocs Material) | The sidebar, per-page ToC and built-in search genuinely address non-linear reading, and they are the only candidate that helps the stated complaint at all. Rejected on identity: the site would be recognisably a default template, and for a portfolio whose differentiator is taste and judgment, looking like everyone else's docs is a real loss. Worth reopening only if search becomes the binding need |
| **Next.js / React** | The option that feels most like progress and delivers least here. The site already does progressive disclosure with `<details>` (nine on the homepage alone); this adds a build, a hydration cost and a dependency tree to reimplement it. The site's own commissioned design review explicitly warned against React-for-presentation, and `CLAUDE.md` treats zero-JS-by-default as a property |
| **Do nothing and treat the complaint as a content problem only** | Half right, and it is the half this stub agrees with — the density fix *is* IA work. Rejected as a complete answer because it ignores the substrate's shaping effect: 12 of 13 pages went without navigation for months specifically because the fix was N hand edits |
| **Migrate now, inside the design-review session** | Rejected on scope discipline. Folding a fourth front into a session about a design review is how scope creep launders itself as consent. The decision gets its own scoped session, which is what this record exists to enable |
